多 Agent 系统的第一个核心问题是：

**谁来决定任务顺序？谁来把上一个 Agent 的输出传给下一个？**

这个角色叫 **Orchestrator（调度员）**。

---

## 调度员的反直觉设计

Orchestrator 有一个反直觉的特点：**它自己什么业务都不干。**

它不翻译、不写作、不做情感分析——它只负责想清楚"谁应该做什么"，然后把任务分出去。

这是职责分离的核心设计：

**Orchestrator 只做：**
- 理解用户意图
- 决定任务顺序和分配
- 把上一步的结果传给下一步
- 汇总最终输出

**Worker 只做：**
- 执行被分配的单个任务
- 不知道也不关心自己是整个流程的第几步
- 不知道也不关心其他 Worker 在做什么

这种分离带来一个实际的好处：想加一个新能力，只需要写一个新 Worker，Orchestrator 和其他 Worker 一行代码不用改。

---

## Workers：各干各的

今天我们建一个文本处理系统，有三个 Worker：翻译、摘要、情感分析。

每个 Worker 只做一件事：

```python
# multi_agent/adv2_orchestrator.py

class TranslatorWorker:
    """只负责翻译，不管任务全局。"""
    def run(self, text: str, target_lang: str = "英文") -> str:
        messages = [
            system("你是专业翻译，只输出翻译结果，不加任何说明。"),
            user(f"将下面的内容翻译成{target_lang}：\n{text}"),
        ]
        return chat(messages, temperature=0.2)

class SummarizerWorker:
    """只负责生成摘要。"""
    def run(self, text: str, max_sentences: int = 3) -> str:
        messages = [
            system(f"你是摘要专家，用不超过{max_sentences}句话概括核心内容。"),
            user(text),
        ]
        return chat(messages, temperature=0.3)

class SentimentWorker:
    """只负责情感分析。"""
    def run(self, text: str) -> str:
        messages = [
            system('分析文本情感，只输出 JSON：{"sentiment": "正面/负面/中性", "score": 0到1, "reason": "一句话原因"}'),
            user(text),
        ]
        return chat(messages, temperature=0.1)
```

注意每个 Worker 的 `run` 方法都是独立的——它不认识其他 Worker，也不知道自己会被谁调用。

## Orchestrator：用 LLM 规划任务

Orchestrator 怎么决定调用哪些 Worker？

最简单的方式是写死规则（if-else）：用户说"翻译"就调 translator，说"总结"就调 summarizer。

但这样只能处理你预设好的情况。用户说"先翻译再分析情感"，if-else 就懵了。

更灵活的做法是**让 LLM 来做这个决策**：

```python
def _plan_tasks(self, request: str) -> list[dict]:
    """让 LLM 理解用户意图，规划需要调用哪些 Worker。"""
    messages = [
        system("""你是任务规划器，根据用户请求输出需要执行的任务列表（JSON 格式）。

可用的 worker：
- translator: 翻译文本，参数 target_lang（目标语言）
- summarizer: 生成摘要，参数 max_sentences（句数，默认3）
- sentiment: 情感分析，无参数

输出格式（只输出 JSON 数组）：
[{"worker": "名称", "params": {}, "use_prev": true/false}]

use_prev=true 表示这一步的输入是上一步的输出。
"""),
        user(request),
    ]
    raw = chat(messages, temperature=0.1)
    # 从 LLM 输出里提取 JSON
    start = raw.index("[")
    end = raw.rindex("]") + 1
    return json.loads(raw[start:end])
```

当用户说"先翻译成英文，再分析英文版的情感"，LLM 会输出：

```json
[
  {"worker": "translator", "params": {"target_lang": "英文"}, "use_prev": false},
  {"worker": "sentiment",  "params": {},                      "use_prev": true}
]
```

`use_prev: true` 表示这一步的输入是上一步的输出——这就是流水线的"信息传递"。

## 执行循环：按顺序跑

拿到任务列表，执行起来很简单：

```python
def run(self, request: str, text: str) -> dict[str, str]:
    print(f"[Orchestrator] 收到请求：{request}")
    tasks = self._plan_tasks(request)
    print(f"[Orchestrator] 任务计划：{[t['worker'] for t in tasks]}")

    results: dict[str, str] = {}
    prev_output = text

    for task in tasks:
        name = task["worker"]
        params = task.get("params", {})
        # use_prev=True 时用上一步的输出，否则用原始文本
        input_text = prev_output if task.get("use_prev") else text

        print(f"  → 调用 {name}({params})")
        output = self._workers[name].run(input_text, **params)
        results[name] = output
        prev_output = output  # 更新，供下一步使用

    return results
```

每个 Worker 只看自己的 `input_text`，不知道 `prev_output` 是怎么来的。Orchestrator 负责维护这个传递链。

## 两种规划方式：LLM vs 硬编码

今天我们用 LLM 来规划任务——灵活，能处理各种自然语言请求。

但有时候不需要这么灵活。如果你的流程是固定的（比如总是"研究 → 写作 → 审核"），那直接写死顺序反而更可靠：

```python
# 固定流程：直接按顺序调用，不需要 LLM 规划
research = researcher.run(topic)
draft = writer.run(research)
final = editor.run(draft)
```

**原则：流程固定用硬编码，流程动态用 LLM 规划。**

不要为了"更智能"而用 LLM，LLM 的规划有时候会判断失误，固定流程不会。
