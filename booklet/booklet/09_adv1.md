# 进阶篇 Day 1：为什么需要多 Agent？——单打独斗的三道墙

> 《AI Agent 进阶：手搓 Multi-Agent 系统》第1篇 · 今日成果：亲眼看到单 Agent 的上下文如何随任务增长，以及多 Agent 分工如何把它压下来

---

7天系列结束后，有读者问我：

> "单 Agent 加上工具、记忆、规划，功能已经不少了。为什么还要多个 Agent？"

这是个好问题。

多 Agent 不是"更酷"或者"更现代"，是因为单 Agent 有三个真实的工程限制，超出这些限制之后，堆 system prompt 和工具都解决不了问题。

今天就来说清楚这三道墙是什么，以及多 Agent 是怎么绕过去的。

---

## 第一道墙：上下文窗口是硬限制

大模型能"看到"的内容是有上限的，这个上限叫**上下文窗口**（context window）。

超过这个上限，要么直接报错，要么模型开始"失忆"——信息还在，但它给出的回答变差了。

这不是理论上的担忧。来跑一个演示：

```python
# multi_agent/adv1_context_demo.py
def demo_single_agent() -> None:
    messages = [system("你是一个全能助手，负责研究、写作、审核全部环节。")]

    steps = [
        ("研究阶段", "研究'人工智能'主题，列出3个核心概念，每条一句话。"),
        ("结构规划", "基于研究，给出一篇科普文章的3段式大纲。"),
        ("写作阶段", "按大纲写出文章正文，约200字。"),
        ("审核阶段", "指出文章最主要的1个问题并给出改进建议。"),
    ]

    for step_name, instruction in steps:
        messages.append(user(instruction))
        tokens_before = estimate_tokens(messages)
        reply = chat(messages, temperature=0.7)
        messages.append({"role": "assistant", "content": reply})
        tokens_after = estimate_tokens(messages)
        print(f"[{step_name}]  {tokens_before:,} → {tokens_after:,} tokens")
```

跑起来你会看到类似这样的数字：

```
[研究阶段]  128 → 512 tokens  (+384)
[结构规划]  512 → 896 tokens  (+384)
[写作阶段]  896 → 1,843 tokens  (+947)
[审核阶段]  1,843 → 2,891 tokens  (+1,048)

最终上下文大小：2,891 tokens
```

一篇小文章，才四步，就用了将近3000 tokens。

如果任务是"写10篇文章"，或者中间有大量工具返回结果，上下文就会以几倍的速度增长，最终撑爆。

**多 Agent 的解法：上下文隔离。**

每个 Agent 只看自己任务相关的信息。Researcher 看不到 Writer 的输出，Writer 看不到 Editor 的评论。每个人的上下文窗口保持在低位。

## 第二道墙：做太多事，专注度下降

你有没有发现：让 AI 同时做三件事，每件事做得都不如单独做一件事好？

这不是偷懒，是认知模式的冲突。

- **研究**要客观全面，不能有立场
- **写作**要有观点有节奏，必须有立场
- **审核**要挑剔批判，专门找问题

三种模式放进同一个 system prompt，AI 就陷入了"到底该听哪条指令"的困境。结果是三件事都做得平庸。

多 Agent 的解法很直接：每个 Agent 有自己的 system prompt，专门为一件事优化。Researcher 的 prompt 写研究风格，Writer 的 prompt 写创作风格，Editor 的 prompt 写批判风格。

各司其职，而不是一个人兼任。

---

## 第三道墙：某些任务天然可以并行

写一篇文章的流程是：研究 → 写作 → 审核。必须串行，因为下一步依赖上一步的结果。

但不是所有任务都有这种依赖。

比如：
- 让三个 Agent 分别从"事实准确性"、"写作风格"、"读者行动建议"三个角度分析同一篇文章
- 让两个 Agent 各自写一个版本，选最好的那个

这些任务之间没有依赖关系，完全可以同时跑。

单 Agent 只能一件件排队，多 Agent 可以并行。进阶篇 Day 4 会专门演示这个——三个任务从6秒缩短到2秒。

完整演示在 `multi_agent/adv1_context_demo.py`，两个函数：

```python
def demo_single_agent() -> None:
    """演示单 Agent 上下文如何随任务增长。"""
    ...

def demo_multi_agent() -> None:
    """演示多 Agent 分工后，每个 Agent 上下文保持在低位。"""
    ...
```

`demo_multi_agent` 里的关键代码：

```python
# Researcher：只有自己的小任务
researcher_msgs = [
    system("你是研究员，只负责整理主题核心要点。"),
    user("主题：人工智能"),
]
research = chat(researcher_msgs)

# Writer：只看研究报告，看不到研究过程
writer_msgs = [
    system("你是写作者，根据研究报告写一段科普段落。"),
    user(f"研究报告：\n{research}"),
]
draft = chat(writer_msgs)

# Editor：只看草稿，不知道前面发生了什么
editor_msgs = [
    system("你是编辑，审核文章并给出一条改进建议。"),
    user(f"文章草稿：\n{draft}"),
]
feedback = chat(editor_msgs)
```

三个 `chat()` 调用，三个独立的 `messages` 列表。每个 Agent 的上下文只包含自己需要的信息。

运行后，你会看到三个 Agent 的上下文合计，比单 Agent 做完所有事的最终上下文要小得多。

## 多 Agent 不是银弹

说完三个优点，也要说清楚代价：

- **调试变复杂**：bug 可能发生在任意一个 Agent，也可能在 Agent 之间的交接处
- **协调有成本**：需要一个"调度员"来管理谁做什么、结果怎么传
- **风格可能不一致**：多个 Agent 产出的内容，语气和风格可能不统一

所以不是所有任务都需要多 Agent。

简单问答、单步生成、短小的工具调用——一个 Agent 就够了。

当任务有明显的**阶段划分**、单个 Agent 的**上下文会爆炸**、或者有**天然的并行机会**，才值得引入多 Agent。
