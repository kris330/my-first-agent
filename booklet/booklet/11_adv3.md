Day 2 的 Orchestrator 和 Worker 直接用函数参数传递信息：

```python
output = worker.run(input_text, target_lang="英文")
```

这很简洁，但有个麻烦：

Orchestrator 必须知道每个 Worker 接受哪些参数，才能正确调用它。`TranslatorWorker` 要 `target_lang`，`SummarizerWorker` 要 `max_sentences`，`SentimentWorker` 什么都不要……

Worker 一旦改了参数，Orchestrator 也必须跟着改。

更深层的问题是：**出了 bug 怎么追踪？**

任务失败了，你怎么知道是哪一步失败的？传入了什么数据？耗时多少？

这些信息，直接传参的方式记不下来。

今天设计一套**通信协议**，解决这两个问题：统一接口 + 可观测性。

## 协议的核心：两个数据结构

协议只有两个东西：`Task` 和 `TaskResult`。

**Task（任务单）**——Orchestrator 下发给 Worker 的标准信封：

```python
@dataclass
class Task:
    task_id:     str            # 唯一 ID，用于追踪
    agent_name:  str            # 目标 Worker 的名字
    instruction: str            # 主要指令（自然语言）
    context:     dict           # 附加数据（上一步的输出、配置参数等）
    created_at:  float          # 创建时间戳，用于计算耗时
```

**TaskResult（结果单）**——Worker 完成任务后回传的标准回执：

```python
@dataclass
class TaskResult:
    task_id:     str            # 和 Task.task_id 对应，便于匹配
    agent_name:  str            # 是哪个 Worker 完成的
    status:      TaskStatus     # DONE 或 FAILED
    output:      str            # 结果内容
    duration_ms: int            # 耗时（毫秒）
    metadata:    dict           # 额外信息（关键词数量、字数等）
```

有了这两个结构，**所有 Worker 的接口变成完全一样的：**

```python
def run(self, task: Task) -> TaskResult:
    ...
```

Orchestrator 不需要了解每个 Worker 的内部细节，只需要构造一个 `Task` 传进去，拿到 `TaskResult`。Worker 内部怎么变，外部调用方式永远不变。

## TaskResult 的两个工厂方法

每次都手动构造 `TaskResult` 很繁琐，`success` 和 `failure` 两个工厂方法帮你自动算耗时：

```python
@classmethod
def success(cls, task: Task, output: str, **meta) -> "TaskResult":
    ms = int((time.time() - task.created_at) * 1000)  # 自动算耗时
    return cls(task.task_id, task.agent_name, TaskStatus.DONE, output, ms, dict(meta))

@classmethod
def failure(cls, task: Task, reason: str) -> "TaskResult":
    ms = int((time.time() - task.created_at) * 1000)
    return cls(task.task_id, task.agent_name, TaskStatus.FAILED, reason, ms)
```

Worker 里用起来很干净：

```python
def run(self, task: Task) -> TaskResult:
    try:
        result = do_something(task.instruction)
        return TaskResult.success(task, output=result)
    except Exception as e:
        return TaskResult.failure(task, reason=str(e))
```

## 协议日志器：知道每步发生了什么

协议的第二个好处是可观测性。每次任务下发和结果接收，都记一条日志：

```python
class ProtocolLogger:
    def on_dispatch(self, task: Task) -> None:
        print(f"  [协议] → 下发任务 {task.task_id[:8]} 给 {task.agent_name}")

    def on_result(self, result: TaskResult) -> None:
        icon = "✓" if result.status == TaskStatus.DONE else "✗"
        print(f"  [协议] {icon} 收到结果 {result.task_id[:8]} 来自 {result.agent_name} ({result.duration_ms}ms)")
```

出了 bug，你能立刻看出：
- 哪个 `task_id` 失败了
- 在哪个 Agent 失败的
- 大概耗时多少
- 不需要在一堆 `print` 语句里翻找

## 实现一个完整的流水线

我们用协议实现一个两步流水线：**关键词提取 → 话题标签生成**。

**两个 Worker，接口完全一样：**

```python
class KeywordExtractorAgent:
    def run(self, task: Task) -> TaskResult:
        messages = [
            system("从文本中提取3-5个核心关键词，用逗号分隔，只输出关键词。"),
            user(task.instruction),        # 主要输入从 task.instruction 来
        ]
        try:
            keywords = chat(messages, temperature=0.1)
            return TaskResult.success(task, output=keywords,
                                      keyword_count=len(keywords.split(",")))
        except Exception as e:
            return TaskResult.failure(task, reason=str(e))


class TagGeneratorAgent:
    def run(self, task: Task) -> TaskResult:
        keywords = task.context.get("keywords", "")  # 附加数据从 task.context 来
        messages = [
            system("根据关键词生成话题标签，格式：#标签1 #标签2，只输出标签。"),
            user(f"关键词：{keywords}"),
        ]
        try:
            tags = chat(messages, temperature=0.3)
            return TaskResult.success(task, output=tags)
        except Exception as e:
            return TaskResult.failure(task, reason=str(e))
```

注意两点：
1. `task.instruction` 放主要的自然语言输入
2. `task.context` 放附加的结构化数据（比如上一步提取出来的关键词）

**Orchestrator 用协议来交接：**

```python
class ContentPipeline:
    def run(self, article: str) -> dict:
        # Step 1：关键词提取
        t1 = Task(task_id=str(uuid.uuid4()),
                  agent_name="keyword_extractor",
                  instruction=article)
        self._logger.on_dispatch(t1)
        r1 = self._extractor.run(t1)
        self._logger.on_result(r1)

        if r1.status == TaskStatus.FAILED:
            return {"error": f"失败：{r1.output}"}

        # Step 2：标签生成（把关键词通过 context 传过去）
        t2 = Task(task_id=str(uuid.uuid4()),
                  agent_name="tag_generator",
                  instruction="生成话题标签",
                  context={"keywords": r1.output})   # 上一步的结果作为 context
        self._logger.on_dispatch(t2)
        r2 = self._tagger.run(t2)
        self._logger.on_result(r2)

        self._logger.print_summary()
        return {"keywords": r1.output, "tags": r2.output}
```

## 加一个新 Worker：改几行就够

这就是统一接口的价值。想加一个"文章摘要 Worker"，只需要：

```python
class SummaryAgent:
    def run(self, task: Task) -> TaskResult:
        messages = [
            system("用一句话概括文章，不超过30字。"),
            user(task.instruction),
        ]
        try:
            summary = chat(messages, temperature=0.3)
            return TaskResult.success(task, output=summary)
        except Exception as e:
            return TaskResult.failure(task, reason=str(e))
```

Orchestrator 里加一行注册，其他代码不动：

```python
self._summary = SummaryAgent()
# 然后在流水线里用 Task/TaskResult 调用就行
```

接口统一的意思就是：**新增功能不需要修改已有代码。**

## 今天的要点

1. `Task` 是下发给 Worker 的任务单，`TaskResult` 是 Worker 回传的结果单
2. 所有 Worker 实现同一个接口：`run(task: Task) -> TaskResult`
3. 主要输入放 `task.instruction`，附加数据放 `task.context`
4. `success()` 和 `failure()` 工厂方法自动算耗时
5. `ProtocolLogger` 记录每步交接，出 bug 能快速定位
